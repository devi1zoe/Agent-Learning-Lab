# 用研究任务理解 Agent 的几个设计概念

本页是 [Stage 0 主课](01-what-is-an-agent.ipynb) 的查阅表，不是要背诵的术语清单。贯穿任务是“研究一个问题并提供已读证据”。

| 概念 | 本任务中的实际对象 | 设计上要回答的问题 |
| --- | --- | --- |
| 目标 | 回答子问题并附来源 | 怎样判断完成，而非只判断模型停止？ |
| 观察 | 工具实际正文、空列表或错误 | 观察有没有进入下一轮模型输入？ |
| 动作 | 模型提出 read_file/search 请求 | 谁校验、谁执行、允许作用在哪些范围？ |
| 状态 | messages、证据池、预算、失败记录 | 哪些本轮清空、哪些跨轮保留？ |
| 计划 | 下一步取证安排或结构化子任务 | 能否根据新观察改变？ |
| 工具 | 程序提供的外部能力 | 接口说明是否准确区分候选与正文？ |
| RAG | 文档切块→索引→检索→基于证据生成 | 相关片段是否真的支持结论？ |
| 记忆 | 有明确写入/检索/删除规则的持久状态 | 来源是用户授权、事实还是模型推断？ |
| Harness | 包裹模型的执行与状态管理 | 怎样控制预算、错误、权限和恢复？ |
| Trace | 原请求、响应、执行与回传 | 能否解释每个动作的前因后果？ |

## 一个重要反事实

把工具返回从“正文已读”换成“文件不存在”，如果下一步仍声称依据该文件回答，就缺少反馈驱动的恢复。把预检索结果直接放进 prompt，则可验证有证据回答，但不能单凭它证明模型选择工具的能力。

记住核心分工：模型提出动作，运行时校验和调度，工具执行，环境提供观察，验收判断任务结果。更多角色不是更高级的证据，更多日志也不自动形成完整证据链。
